# Second Brain Kit Base

A starter kit that turns a coding agent (Claude Code, Gemini, Codex) into a personal AI operating system: context files, a connections registry, a standing memory, a decisions log, an LLM-maintained wiki, a projects workbench, and four skills (onboard, audit, os-audit, level-up).

De-branded internal base, kept as reference material and as a candidate skeleton for client installs.

## Unbound handoff

Unbound publishes **one** web `brain.md` (setup + routine). This repository is the starter **kit** agents clone. Install/loop playbooks are not kept as `brain.md` / `loop-setup.md` / `loop-routine.md` in this repo.

---


# The course: from zero to a working AI OS

Five lessons. The first four each wire in a pillar (Context, Connections, Capabilities, Cadence); the fifth turns the build into a daily habit. The walkthrough uses Claude Code inside VS Code, but any coding agent works (Codex, Gemini CLI, etc.). The folder structure, the CLAUDE.md file, the skills: all of it ports over. If you use a different tool, only the install steps change.

## Lesson 1: Install, clone, onboard

This is where you stop thinking and start building. By the end, your AI OS has the foundational context it needs to start being useful.

### Step 1: Install VS Code

Search "VS Code", download, install. Free.

### Step 2: Install the Claude Code extension

Open VS Code. Click the extensions icon on the left. Search "Claude Code", install it, and log in with a paid Claude subscription when prompted. Once logged in, open the Claude Code panel: you now have a chat interface inside your editor.

### Step 3: Create your AI OS folder and clone this repo

Make a new folder anywhere ("AI OS" or whatever you like). In VS Code: File > Open Folder, open it. Then paste this repo's URL into the chat with "clone this repo into the current project" and hit allow. Folders and files populate on the left.

### Step 4: Folder walkthrough

Every folder has a purpose. `CLAUDE.md` is the master prompt: it loads into every session and tells the agent who you are, what skills exist, and where things live. It's a living document; as you add folders, you update it so the agent can route.

| What | Purpose |
|---|---|
| `CLAUDE.md` | Operating manual and router. Loaded every session. Filled by `/onboard`. |
| `aios-intake.md` | The 7-question intake contract. Edit it and re-run `/onboard` any time. |
| `.claude/skills/` | The project's brain: reusable recipes the agent can run (`/onboard`, `/audit`, `/os-audit`, `/level-up`). |
| `context/` | About you, your business, your priorities. `/onboard` writes the first versions. |
| `connections.md` | Registry of every system the OS can reach. |
| `memory/` | Standing rules and durable facts, one per file. The `MEMORY.md` index is imported every session; a rule not in the index is invisible. |
| `decisions/log.md` | Append-only record of meaningful decisions and why. |
| `wiki/` | Your second brain: an LLM-maintained wiki. Schema and ingest/query/lint workflows in `wiki/CLAUDE.md`. |
| `projects/` | Workbench for real code repos and client deliverables. Git-ignored; conventions in `projects/README.md`. |
| `references/` | Lookup-heavy material: frameworks, API guides, voice samples. |
| `archives/` | Old or deprecated files. Don't delete, archive. |
| `audits/` | Dated reports generated by `/audit` and `/os-audit`. Git-ignored, machine-local. |

### Step 4.5: Make it yours

This repo is a TEMPLATE. Before anything personal goes in it, the onboarding will repoint it to a private repo you own (template stays connected as "upstream" so you can pull kit improvements later) and install a small sync routine so your copy stays committed, backed up, and current across machines without you thinking about it.

### Step 5: Run the onboarding skill

In the chat, type something like:

> "I just cloned this repo. I want to set up my AI operating system. My name is ___. Can you help me get onboarded?"

The agent picks up the `/onboard` skill and runs a seven-question interview: who you are and what you sell, samples of your writing so it learns your voice, your top priorities for the next 90 days, and four more. Answer in real detail; the more context, the better. Voice dictation helps: it's faster to dictate two paragraphs than to type one.

### What just happened

`/onboard` scaffolded your day-one file set in `context/` (about you, about the business, priorities) and filled the placeholders in `CLAUDE.md`. Start a fresh session and ask "what should I focus on this week?" and the agent reads those files and gives a real answer instead of a generic one. That's the Context pillar wired in.

### Lesson 1 takeaways

- VS Code + a coding agent extension is the whole setup.
- Every folder has a purpose. `CLAUDE.md` is the master prompt and router.
- Run `/onboard` and answer the seven questions in depth.

## Lesson 2: Connecting your tools

Context without connections is just a journal. This lesson is where your AI OS gets eyes and hands.

### API vs MCP, and why API is the default

Most AI models default to suggesting an MCP server when you want to connect a tool. MCP works, but it loads every function the tool offers into your context, even ones you don't need. That eats tokens fast.

Default to the tool's API directly. Tell the agent: "I want to use this tool's API because it's more token-efficient than an MCP server. Research the API docs and create a markdown reference file with all the endpoints I might use." Now the agent has a local reference in `references/` it can look up endpoints from. No web searches, no MCP bloat.

### Create a dedicated AI account

Don't give your AI OS your personal account credentials. Create a separate account on the platform specifically for the AI. Why:

- **Scoped permissions.** Maybe the AI account only gets read access, never write.
- **Traceable usage.** If the AI is making API calls or spending money, you see exactly which automation did what.
- **Contained blast radius.** If something goes wrong, damage is limited to what that scoped account can touch.

### Use a .env file for secrets

Never paste an API key into the chat. Tell the agent: "Create a .env file with placeholders for the keys you need. I'll fill them in." This kit's `.gitignore` already excludes `.env`, so secrets stay local. The agent reads them when it needs to make a call.

### The connection flow (same for every tool)

1. Create a dedicated account on the platform, scoped to what the AI actually needs.
2. Generate an API key with the right scope.
3. Have the agent add a placeholder to `.env`; paste your key in yourself.
4. Have the agent research the API and write `references/{tool}-api.md`.
5. Add a row to `connections.md`: what's connected, what it's authorized for, when it was last verified.
6. Test with a real task. If it fails, have the agent update the reference doc so the same mistake never happens twice. Failures are a feature here.

Example: a task manager like ClickUp. Create the AI account, grab the API token from the tool's settings, walk the six steps, then test with something real ("run a workload snapshot across the team").

### Google Workspace CLI

If you live in Google (Drive, Docs, Sheets, Gmail, Calendar, Slides), one open-source tool unlocks all of it: the Google Workspace CLI, free, with 100+ built-in workflow skills. Find its GitHub repo, give the agent the link, and say "help me install this CLI." It walks you through creating a Google Cloud project, an OAuth client, and credentials; then `gws auth login` and you're done. From there: search Drive, triage Gmail, build Sheets trackers, generate Slides from your own assets. Everything it creates lives in your Drive, reachable by any other agent on your team.

### The improvement loop

Once your first connection is wired, run `/audit`. It scores the OS against the Four Cs and shows the biggest gaps (a low Connections score on day one is normal). Then run `/level-up`: it interviews you about your week and hands you the next thing to automate. Audit shows the gaps; level-up picks which one to fix next.

### Lesson 2 takeaways

- APIs over MCPs when possible: token-efficient and cleaner.
- Dedicated AI accounts with scoped permissions, always.
- Secrets go in `.env`, never in chat.
- One tool at a time; every tool gets a reference doc and a `connections.md` row.
- `/audit` + `/level-up` is the loop that tells you what to wire next.

## Lesson 3: Building capabilities with skills

Capabilities is where the AI OS goes from "smart database" to "actual employee." A skill turns any repeated workflow into a single command.

### What a skill is

A folder under `.claude/skills/skill-name/` containing a `SKILL.md`: YAML frontmatter on top (name, description), plain-markdown instructions below. Think recipe. If you write a LinkedIn post the same way every time (research, graphic, copy, review, post), bundle those steps into a skill; then "/linkedin-post" or plain natural language runs the whole thing. Skills aren't just text generators: they can run scripts, call APIs, use sub-agents, and trigger other skills.

### Anatomy

1. **Frontmatter** (required): name + description. This is what the agent scans to decide when to trigger.
2. **Instructions**: the step-by-step SOP.
3. **Supporting files** (optional): reference docs, scripts, assets. Can live in the skill folder or anywhere in the project, as long as SKILL.md points at the path.

### Progressive context loading

Why 30 skills don't blow your token budget: the agent reads only frontmatter when scanning (~100 tokens per skill), the full SKILL.md only after picking one (~1-2k tokens), and supporting files only if the specific run needs them.

### The six-step build framework

1. **Name and trigger**: what's it called, what natural language fires it.
2. **Goal**: one sentence, what does it produce.
3. **Process**: if you did this manually, exactly what would you do, in order.
4. **Reference files**: what context, style guides, or API docs it needs.
5. **Rules**: what could go wrong; add guardrails for the failure modes.
6. **Improvement loop**: first runs are rough. Watch it work, give feedback, refine. By run 10-20 it's locked in.

You don't have to write it from scratch: tell the agent "interview me and build this skill." It asks what problem you're solving, how it should trigger, and what the steps are, then writes the file for you.

### When to build one

Done the same thing twice and you'll do it again: skill candidate. Repeating the same corrections across prompts ("stay in my voice", "use this brand color"): bundle those rules into a skill.

### Debugging map

| Symptom | Fix |
|---|---|
| Wrong steps or order | Edit the SKILL.md instructions |
| Missing tone/style | Add a reference file |
| Same mistake twice | Add an explicit rule |
| Keeps re-searching the same thing | Hardcode that data in a reference doc |
| Works but could be better | Run it more; each nitpicked run adds polish |
| Not triggering | Make the YAML description more specific |
| Triggering too often | Restrict to slash-command-only invocation |

### Project-scoped vs global

`.claude/skills/` in a project only exists there. `~/.claude/skills/` in your home directory is global: works in every session on your machine. Global for universals (voice, brand assets, a design skill you use everywhere); project-scoped for one workflow.

### Lesson 3 takeaways

- Skills are markdown recipes the AI runs when triggered.
- Progressive context loading keeps them token-efficient.
- Have the agent interview you instead of writing from scratch.
- First runs are rough; iterate. Project vs global by how universal it is.

## Lesson 4: Routines, schedules and loops

The last C. Cadence is everything that runs while you sleep: scheduled tasks, triggered automations, daily loops, reminders. This is what gives the OS a heartbeat.

### Push your AI OS to GitHub first

Get the OS into a **private** GitHub repo. Two reasons: sync (clone it onto a second machine and the OS is portable) and cloud routines (they run off a cloned repo; no repo, no routines). This kit's `.gitignore` already excludes `.env`, so secrets stay local. Verify before the first push.

### Local scheduled tasks

Created in the Claude desktop app. They run on your machine while the app is open, as often as every minute, and can call any skill you've built. Good for things that should fire constantly while you're working but don't need to survive the laptop closing.

### Cloud routines

Run on Anthropic's infrastructure: laptop closed, machine off, doesn't matter. Fire on a schedule (minimum hourly), via API call, or on a GitHub event. Gotchas to know up front:

- **`.env` doesn't transfer.** The cloud environment can't see your local file; set env vars in the routine's cloud environment settings.
- **Network access modes.** Default "trusted" only reaches verified domains; switch to "full" only after reading the security docs.
- **Resource and run limits.** Each run gets a bounded VM, and plans cap daily runs. Limits change; check current docs. If your repo is huge, consider a separate repo per routine.

A routine is just you typing a prompt into Claude Code at a scheduled time. Which is why the prompt matters:

**Routine prompts must be one-shot.** You're not around to redirect. "Pull my comments and tell me what to focus on" is too vague for an unsupervised run. "Run the /comment-analysis skill, pull the 50 most recent comments, output themes + sentiment + top three priorities, post to my ops channel" can run on its own.

### The /loop feature

Loops are short-burst recurring tasks inside a single session. Two flavors: recurring intervals ("every 10 minutes, check for new messages"; runs up to a few days, then auto-cleans) and one-time reminders ("at 3pm, remind me X"; fires once, deletes itself). Loops die with the session. Great for a heartbeat during active work; wrong tool for anything long-term.

### When to use what

| Need | Tool |
|---|---|
| Short bursts during active work (days, not weeks) | `/loop` |
| Recurring, machine on, runs frequently | Local scheduled task |
| Recurring, must run with laptop closed | Cloud routine |

Whatever you schedule, follow this kit's durability rule (`EXPANSIONS.md`): register every job with a committed setup script, so a machine rebuild is one script per job and `/os-audit` can tell what's supposed to be running.

### Lesson 4 takeaways

- Private GitHub repo enables sync and cloud routines. `.env` stays out.
- Local tasks need your machine on; cloud routines don't, but need explicit env vars and the right network mode.
- Loops are for active sessions; routines are for long-term cadence.
- Routine prompts are one-shot prompts. Be specific enough to succeed unsupervised.

## Lesson 5: Knowledge wiki, dashboards, and daily use

Four Cs wired. This last lesson makes the OS feel like a real second brain you use every day.

### The LLM Wiki pattern (Karpathy)

Instead of a vector database with embeddings and a RAG pipeline, give the AI a folder of markdown files and let it organize them itself. This kit ships the pattern in `wiki/`:

- `wiki/raw/`: dump source documents (articles, transcripts, PDFs, notes). Immutable.
- `wiki/sources/`, `entities/`, `concepts/`, `syntheses/`: the AI-written, cross-linked pages.
- `wiki/index.md` + `wiki/log.md`: what's in the wiki and what's been ingested.
- `wiki/CLAUDE.md`: the schema that keeps the agent a disciplined maintainer.

Drop a file into `raw/`, say "ingest". The agent reads it, writes a source page, updates every entity and concept page it touches, cross-links them, and updates the index. One ingest can touch 5-15 pages; that's the point. Maintenance is a periodic "lint the wiki": find contradictions, fill gaps, prune duplicates. Cost is near zero. Works to a few thousand documents; past that, consider real search tooling.

### Obsidian as the optional front-end

Free. Point a vault at the `wiki/` folder and you get a visual graph of every concept and its connections: clickable links, visible hubs, obvious orphans. The wiki works fine without it; the AI doesn't care about the UI. This kit uses standard markdown links (not wikilinks), so pages stay readable on GitHub too.

### Dashboards as proofs-of-concept

Claude's artifacts can turn any wired connection into a live dashboard in minutes: finance snapshot, weekly commitments, meeting summaries. They're rough by design. The value is speed: spin one up in 5 minutes, see if you actually check it, and only invest in a custom build if you do. POC mindset: prove the concept cheap, invest only in what proves out.

### The daily and weekly loops

- **Every morning**: "help me plan my day." Good answer: great. Missing context: note the gap and patch it.
- **End of day**: which skills did I use? What did I correct? What did I copy-paste manually that should be automated?
- **Friday**: run `/audit`, then `/level-up`. If a skill ran daily this week, ask whether it should become a scheduled routine and run while you sleep.

### Workflows beat agents most of the time

Most business processes don't need an autonomous agent. They need a deterministic workflow with maybe one AI step inside. When in doubt, build the simplest thing that works: a Python script, a scheduled routine, a skill that calls one API. Save the agentic stuff for parts that actually need judgment.

### Three success criteria

1. **People start asking your AI OS instead of you.** Same data, better memory, never sleeps.
2. **You stop opening new tabs.** Most work happens inside the agent, not across 15 browser tabs.
3. **Knowledge leaves your head.** No sticky-note stack; the system holds it and reminds you when it matters.

Two of three true within the first month: the OS took.

### Personal before team

You can't scale a system you haven't lived in. Once your personal AI OS works, a team can build around it: data structured for AI, workflows documented as skills, connections mapped. Start with you.

### Lesson 5 takeaways

- The LLM Wiki turns markdown folders into a self-organizing knowledge graph; this kit ships it in `wiki/`.
- Obsidian is a nice optional viewer, nothing more.
- Dashboards: POC first, custom build only if the POC gets used.
- Daily and weekly loops turn the build into a habit.
- Workflows beat agents most of the time; default to the simplest thing.

## Lesson 6: Daily rhythm, company brains, and teaching your OS

### Start every session with /prime

Make it a habit: open a session, type /prime, read the one-screen readiness report (what rules are loaded, what changed recently, any watch-outs), THEN give it your task. A primed session starts with your full context instead of rediscovering it mid-task.

### Set up a company brain

Run /onboard and answer "company" at the fork. Give it the company's website; it scrapes the site, drafts the brand interview (facts, ideal customers, frame, voice, from the question bank in references/brand-questions/), and confirms every answer with you one at a time. Confirmed answers land in companies/<slug>/ with a provenance line each. From then on, any customer-facing work for that company starts from its confirmed profile, not from guesses.

### Let the OS learn, with you in the loop

Your AI watches for capture moments: you correct it, you say "we always/never...", a decision gets made, a fact changes. When it spots one, it asks in ONE line whether to save it (a memory rule, a company fact, a decision entry). It never saves silently. Say yes and the rule shapes every future session; say no and it drops it. Before long sessions end, it sweeps once: "anything worth saving?"

### Works in any agent harness

The root manual is AGENTS.md, the open standard read natively by Codex, Gemini (via the committed settings file), Grok, Kimi, and most coding agents; Claude Code reads it through the one-line CLAUDE.md shim. Standing memory and your pinned brand are INLINED into it by scripts/compose.py, so they load everywhere without any import features. Skills live in .agents/skills/ (the shared standard) with mirrors for Claude and command wrappers for Gemini. One repo, any harness.

### Lesson 6 takeaways

- /prime first, task second. Every session.
- Company brains are built by confirmation, not dictation: the AI drafts from the website, you approve one answer at a time.
- The OS only learns what you approve. Every rule in memory/ got a yes from you.
